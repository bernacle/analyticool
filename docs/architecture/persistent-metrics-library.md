## 1. Boundary and explicit ADR refinements

BRU-492 owns **dashboard authentication and metadata authorization**. BRU-493 later adopts that principal/membership boundary for source execution; BRU-494 owns embed authorization. References assigning all real authentication to BRU-493 are refined accordingly. Next.js dashboard actions/handlers are internal product operations, not a hosted metrics API.

Keep core pure and the React SDK stateless. Put the first server implementation in `apps/demo` with server-only imports, a small data-access module and versioned SQL migrations. Do not add a provider abstraction, repository framework, ORM, separate service or second metric language. Reuse the supported collected-revenue definition; operational net receipts does not gain a new Studio lifecycle here.

**Explicit refinement to BRU-464 §2h:** Supabase manages the dashboard session; Next.js alone reads and refreshes its cookies. “Server-side session” does not require an additional Analyticool session registry. Preserve HttpOnly, Secure and SameSite cookies. This changes the ownership/detail of the session design, not its security requirements or provider.

BRU-493/494, customer source credentials, source execution/connectors, hosted APIs, embed tokens, scheduled refresh and deployment remain excluded. Store source references only. Refresh metadata is explicitly `not_executed`/unknown until an actual executor supplies it. A durable publication is an internal record; it does not make a metric publicly reachable.

## 2. Authentication: server-only Supabase integration

Use `@supabase/ssr`'s `createServerClient` and `@supabase/supabase-js` on the server. Enforce cookie options in the `getAll`/`setAll` adapter: HttpOnly, Secure outside explicit loopback development, SameSite=Lax, Path=/, no Domain. Apply these to every chunk and deletion; cap expiry to the remaining absolute session lifetime in `setAll` because the SDK can override `cookieOptions.maxAge`. Never expose tokens in props, JSON, localStorage, logs or client bundles. Client React may call authenticated Next.js operations; it never calls Supabase directly.

Rationale: Supabase documents HttpOnly tokens for a server-only application. Its standard browser/SSR guide assumes browser token access, whereas its server SDK accepts custom cookie options. Applying that SDK adapter without a browser client is our design inference, to be verified with the selected package versions. It avoids both relaxing HttpOnly and building another session store. See [session guidance](https://supabase.com/docs/guides/auth/sessions), [SSR guidance](https://supabase.com/docs/guides/auth/server-side/advanced-guide), and the [SDK cookie implementation](https://github.com/supabase/ssr/blob/main/src/cookies.ts).

- Start with email/password login for operator-created Supabase users; disable public signup. No invitations, OAuth, recovery UI or organization management. Account recovery/provisioning stays an operator responsibility.
- Refresh in the Next.js request layer that can write cookies; preserve all cookie/cache headers on responses and redirects. Use the SDK's rotation handling, not handwritten refresh-token rotation. Concurrent refresh and rotation failures require integration tests.
- Every protected server operation verifies the token using Supabase `getClaims`, checks the current account through `getUser`, and authorizes current membership. Cookie deserialization/`getSession`, layouts and Proxy alone never grant authority. Verify the configured issuer/audience/expiry and use verified subject/session claims only. [Supabase method guidance](https://supabase.com/docs/guides/auth/server-side/creating-a-client).
- Require the verified subject and `session_id` to match an active Supabase `auth.sessions` row at database access. Use a narrowly granted read-only predicate; never give the runtime role broad access to Auth tables or alter the managed Auth schema. Check session age explicitly: proposed defaults are a 15-minute access token and an 8-hour absolute login lifetime, requiring reauthentication thereafter. Refresh must not reset that lifetime. Cookie age alone is not expiry enforcement.
- Successful logout revokes the current Supabase session and clears every session-cookie chunk. Previously captured tokens must then fail the session-row check. If remote revocation fails, clear browser cookies but report that server revocation was not confirmed. Expiry, invalid account/session, Auth failure or database failure denies protected access; never fall back to the fictional workspace. Supabase documents session-row correlation and delayed expiration cleanup in its [session reference](https://supabase.com/docs/guides/auth/sessions).
- Keep Auth clients request-scoped; disable shared caching/ISR of authenticated pages, responses and session refreshes (`private, no-store`). Validate same-origin mutations, including login/logout, and use Next.js Server Actions' Origin checks plus explicit checks for any route handlers. Allowlist redirects. Preserve Supabase login protections; no local authentication bypass outside a conspicuously separate fixture-only demo.

Before building the feature, a local integration spike must prove HttpOnly login, refresh, concurrent refresh, logout and server-only account access with pinned versions. Failure is a design gate: revisit this ADR explicitly instead of silently dropping cookie protections. This spike belongs to authorized preparation/PR 1, not this documentation change.

## 3. Workspace permissions and database access

| Role     | Read metric/history/evidence | Create, edit, clarify, submit, reject, duplicate, revise | Approve | Publish             |
| -------- | ---------------------------- | -------------------------------------------------------- | ------- | ------------------- |
| `viewer` | Yes                          | No                                                       | No      | No                  |
| `editor` | Yes                          | Yes, within lifecycle rules                              | No      | No                  |
| `admin`  | Yes                          | Yes, within lifecycle rules                              | Yes     | Yes, after approval |

No dashboard role creates workspaces or changes memberships. Operators provision those through separately privileged, audited tooling. An admin may approve their own work: record author, approver, effective role, session reference, database time and an explicit self-approval flag. Publication is another explicit action with its own actor/time. No implicit approval on import, duplication or revision.

Resolve workspace selection only against the authenticated user's current membership rows. A URL/form selection is an untrusted selector, never authority; omit workspace/actor/role/status overrides from mutation payloads. Scope every lookup, join, search/count, evidence reference, idempotency receipt and publication pointer. Foreign and missing resources have the same response shape. Unknown roles and missing context deny access.

Use `pg` with a dedicated non-owner, non-superuser, non-BYPASSRLS runtime login. It owns no objects, cannot assume the migration/owner role, create schema objects, alter policies or write memberships. Migrations use a different credential. Keep metadata in a schema not exposed through the Supabase Data API; browser/anon/authenticated Data API roles receive no metadata access.

Enable and FORCE RLS on workspace-owned tables. Bind verified subject/session and the membership-validated workspace as transaction-local context, with missing/invalid context denying access. Policies enforce current membership in addition to server checks; foreign keys include workspace and metric identity. Use transaction-local settings to prevent pool leakage. The backend issuing that context is trusted: possession of arbitrary SQL access under its database credential could forge context. RLS does not defend a compromised backend credential.

Grant runtime SELECT only as required and EXECUTE on a small explicit set of metadata commands; no direct table DML for versions, publications, audit or receipts. Where SECURITY DEFINER is necessary, use a NOLOGIN/NOBYPASSRLS owner subject to FORCE RLS, fixed safe search_path, schema-qualified references, explicit scope/role checks and revoked PUBLIC EXECUTE. Separate the minimal Auth-session predicate's privileges. Test all of this under the actual runtime login, including owner/role inheritance and function grants. [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security) and [function security](https://supabase.com/docs/guides/database/functions).

## 4. Durable identity, lifecycle and audit

Use small concrete records; avoid a generic artifact platform:

| Record                 | Required invariant                                                                                                                                                                                                |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Workspace + membership | Unique user/workspace membership with one known role; runtime cannot provision it.                                                                                                                                |
| Metric                 | Stable workspace asset UUID, distinct from the core calculation ID and per-revision proposal ID; optional current publication pointer.                                                                            |
| Metric version         | Unique `(workspace, metric, version)`; proposal ID, strict core payload, schema version, content digest, lifecycle state, concurrency counter and predecessor.                                                    |
| Metric event           | Append-only creation/edit/review/approval/rejection/revision/publication evidence, authenticated actor/role/session, database time, before/after state/counter, request ID and exact content/evidence identities. |
| Publication            | Insert-only record referencing the exact approved version, approval event and digest; actor/time; uniqueness per version.                                                                                         |
| Mutation receipt       | Workspace/actor/key uniqueness, action/target/payload fingerprint, committed outcome and event reference. No tokens or arbitrary response bodies.                                                                 |

Retain `draft`, `needs_clarification`, `ready_for_review`, `approved`, `rejected` and the separate publication record. Do not introduce a `reviewed` state. Reuse existing core validation and pure transition rules, factoring them for server use if needed while preserving the local capability wrapper. Loading validated rows does not resurrect WeakSet authority; the authorized database transaction establishes durable authority. Never export a helper that blesses arbitrary parsed approvals.

Draft edits return to draft and invalidate readiness. Freeze reviewed content on approval; approval, publication and audit records cannot be updated/deleted by runtime commands. Revision is allowed from a published version and creates a new draft, clears approval, and never rewrites its predecessor. Preserve core's single direct successor rule, including a rejected successor; a further attempt can be duplicated into a new metric lineage until that policy is explicitly changed. Duplication creates a separate asset at v1 without copied authority. Keep old publications retrievable by exact version; moving the current pointer on a later publication cannot rewind it.

Define one fixed-schema serialization for SHA-256: include reviewed question/name, calculation policy, bindings, relationships, assumptions, clarification answers and explanatory evidence; exclude lifecycle state, actor/time and the digest field. Store the serialization version. Approval pins the exact digest and available evidence references at that time. Evidence added later does not retroactively become reviewed. Equal digests across workspaces grant no access. Store bounded metadata/allowlisted fixture references, not customer rows or arbitrary fetched URLs; approval and fixture verification remain separate claims.

## 5. Transactions, concurrency and retry rules

Each command uses one checked-out `pg` client and one bounded transaction; never scatter a transaction across pool.query calls. Begin at READ COMMITTED, bind local context, validate session, and lock/recheck current membership before data access. Membership-changing operator commands use conflicting row locks so revocation and mutations serialize. Lock the metric row for version allocation, then the version row; use the same order everywhere. Recheck expected state, version counter and digest after acquiring locks. Core validates meaning; SQL constraints/commands defend durable lifecycle invariants. [node-postgres transaction contract](https://node-postgres.com/features/transactions).

Allocate versions under that lock with a unique database constraint, never an unlocked `max(version)+1`. Commit content/state changes, approval/publication, current pointer, audit event and idempotency receipt together. A failure anywhere rolls everything back. Read operations also use scoped transactions so RLS context cannot leak between requests.

Every mutation carries a bounded opaque idempotency key and expected concurrency counter. A unique `(workspace, actor, key)` receipt serializes identical concurrent requests. Matching action/target/payload replays the original committed outcome after current authorization is checked; a different fingerprint conflicts. Reusing another actor/workspace's key reveals nothing. Keep receipts for the lifetime of the metric in this MVP. A lost COMMIT response is resolved by retrying the same key, not issuing a new mutation. Stale counters and invalid state return conflicts; bounded deadlock/serialization retries reuse the key and reauthorize. Set local statement/lock/idle timeouts, rollback/discard broken connections and return redacted errors. No background retry service.

Transactional business events cover committed changes; failed or denied requests produce redacted operational diagnostics, not a partial business event. This audit is protected against the runtime role, not against a database administrator. No delete/retention-management feature in this issue; do not claim tamper-proof or signed evidence.
